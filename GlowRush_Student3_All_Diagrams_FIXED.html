A presentation-ready Mermaid collection for database, API, events, payment, order, reliability, security and observability. The diagrams use one consistent GlowRush vocabulary and are designed to explain the critical 10,000-customer / 100-unit flash-sale scenario without turning each diagram into a wall of boxes.

DatabasePostgreSQL is the durable transactional source for business records.
PaymentIdempotency + unique provider references prevent duplicate payment effects.
RecoveryPaymentConfirmed events survive temporary Order Service failure.
OrderExplicit order states make recovery and lifecycle ownership explainable.

04 · Payment State Diagram

Explicit payment states avoid ambiguous treatment of retries and timeouts.

stateDiagram-v2 [*] --> INITIATED INITIATED --> PENDING : provider call PENDING --> SUCCEEDED : gateway success PENDING --> FAILED : definitive failure PENDING --> TIMED_OUT : no response TIMED_OUT --> PENDING : safe retry TIMED_OUT --> RECONCILIATION : retry limit reached RECONCILIATION --> SUCCEEDED : provider confirms RECONCILIATION --> FAILED : provider confirms failure SUCCEEDED --> [*] FAILED --> [*] RECONCILIATION --> [*] : resolved
A timeout is not treated as an automatic payment failure; the design supports safe retry and reconciliation.

05 · Payment Timeout & Reconciliation Sequence

Shows how GlowRush avoids charging twice when a provider response is ambiguous.

sequenceDiagram autonumber participant C as Checkout participant P as Payment Service participant G as Payment Gateway participant DB as PostgreSQL participant R as Reconciliation Worker C->>P: Charge request + idempotency key P->>G: Create payment G--xP: Timeout / no response P->>DB: Mark payment TIMED_OUT P-->>C: Payment status = pending verification P->>P: Apply backoff policy P->>G: Safe retry / status lookup alt Provider confirms success G-->>P: Success + same transaction reference P->>DB: Mark payment SUCCEEDED else Provider remains ambiguous G--xP: No decisive response P->>R: Create reconciliation case R->>G: Query provider status G-->>R: Final provider status R->>DB: Reconcile payment end

06 · Duplicate Payment / Idempotency Sequence

Repeated client requests produce one payment effect and reuse the original result.

sequenceDiagram autonumber participant C as Customer participant P as Payment Service participant I as Idempotency Store participant G as Payment Gateway participant DB as PostgreSQL C->>P: Payment request (key = K123) P->>I: Lookup K123 I-->>P: Not found P->>G: Create payment G-->>P: Success, transaction = T900 P->>DB: Persist payment T900 P->>I: Store result for K123 P-->>C: Success(T900) C->>P: Duplicate payment request (key = K123) P->>I: Lookup K123 I-->>P: Existing result T900 P-->>C: Return original result Note over P,G: Gateway is NOT called again

07 · Payment Success + Order Service Failure

Critical jury scenario: payment remains durable and the order is recovered asynchronously.

sequenceDiagram autonumber participant C as Customer participant P as Payment Service participant G as Payment Gateway participant DB as PostgreSQL participant MQ as RabbitMQ participant O as Order Service participant R as Reconciliation C->>P: Pay + idempotency key P->>G: Authorize / capture G-->>P: SUCCESS P->>DB: Persist payment SUCCESS P->>MQ: PaymentConfirmed(eventId=E1) MQ--xO: Order Service unavailable Note over MQ,O: Event remains retryable MQ-->>O: Redeliver PaymentConfirmed(E1) O->>DB: Idempotently create order O-->>MQ: Ack E1 O->>MQ: OrderCreated MQ-->>C: Async notification path alt Message or state remains unresolved R->>DB: Find unmatched successful payments R->>O: Reconcile missing order O->>DB: Create / repair order idempotently end
