Student 2 inventory & concurrency architecture

A complete Mermaid visual set for the critical stock-consistency module: inventory authority, reservation lifecycle, atomic concurrency, idempotency, expiry/release and recovery. The diagrams are intentionally separated so each one answers a single jury question clearly.

Stock authorityInventory & Reservation Service is the final authority for available stock.
Consistency pointAtomic conditional update prevents more successful reservations than stock.
IdempotencyThe same request key returns the existing business result instead of creating another reservation.
Reservation TTLFive-minute backend expiry releases unpaid reservations; browser navigation is not cancellation.

04 · Purchase / Reservation Sequence

Normal successful path from an admitted Buy Now request through the inventory transaction.

sequenceDiagram autonumber participant U as Customer participant S as StormShield participant GW as API Gateway participant R as Reservation Service participant I as Inventory Service participant D as PostgreSQL participant MQ as RabbitMQ U->>S: Buy Now + idempotency key S-->>U: Admission token U->>GW: POST /api/v1/reservations GW->>R: Validate token + request R->>I: Reserve 1 unit I->>D: Atomic conditional UPDATE alt available_quantity >= 1 D-->>I: affected_rows = 1 I-->>R: Reservation successful R->>D: Persist reservation = RESERVED R->>MQ: ReservationCreated R-->>U: reservationId + expiresAt else stock unavailable D-->>I: affected_rows = 0 I-->>R: Reservation failed R-->>U: OUT_OF_STOCK / RESERVATION_FAILED end

05 · Reservation State Diagram

Canonical reservation lifecycle including payment failure and timeout release paths.

stateDiagram-v2 [*] --> AVAILABLE AVAILABLE --> RESERVED : reservation created RESERVED --> PAYMENT_PENDING : checkout started PAYMENT_PENDING --> CONFIRMED : payment confirmed CONFIRMED --> SOLD : order finalized PAYMENT_PENDING --> PAYMENT_FAILED : definitive failure PAYMENT_FAILED --> RELEASED : inventory released RESERVED --> TIMEOUT : expiresAt reached TIMEOUT --> RELEASED : expiry worker RELEASED --> AVAILABLE : unit returned to pool SOLD --> [*]
Canonical shared state sequence: AVAILABLE → RESERVED → PAYMENT_PENDING → CONFIRMED → SOLD, with PAYMENT_FAILED and TIMEOUT release paths.

07 · 10,000 → 100 Concurrency Architecture

The central flash-sale contention model: admission controls the request rate, while the database transaction is the final inventory consistency point.

08 · Last-Item Race Condition

Two customers contend for one remaining unit; only one transaction can satisfy the atomic condition.

sequenceDiagram autonumber participant A as Customer A participant B as Customer B participant I as Inventory Service participant DB as Inventory Row par A and B arrive concurrently A->>I: Reserve final unit B->>I: Reserve final unit end I->>DB: UPDATE ... SET available = available - 1 WHERE available >= 1 I->>DB: UPDATE ... SET available = available - 1 WHERE available >= 1 DB-->>I: One request affected_rows = 1 DB-->>I: Other request affected_rows = 0 I-->>A: Winner → ReservationCreated I-->>B: Loser → RESERVATION_FAILED / OUT_OF_STOCK Note over DB: Database serialization / atomic condition makes the winner deterministic
The losing request never creates a successful reservation after inventory reaches zero.
