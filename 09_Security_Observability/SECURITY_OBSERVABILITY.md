# GlowRush — Security & Observability Architecture

> **Version:** 1.0 | **Owner:** Student 1 (System Architect)

---

## 1. Security Architecture

The GlowRush platform employs a defense-in-depth strategy to protect customer data, prevent fraudulent reservations, and ensure platform stability during extreme load.

### 1.1 Edge Security

| Component             | Configuration / Strategy                                                                 |
| --------------------- | ---------------------------------------------------------------------------------------- |
| **AWS WAF**           | Blocks OWASP Top 10 vulnerabilities (MongoDBi, XSS, etc.). Implements IP reputation blocking and basic bot detection to filter malicious traffic before it hits the ALB. |
| **CloudFront CDN**    | Enforces HTTPS (TLS 1.3). Hides origin servers from direct internet access. Protects against volumetric DDoS attacks. |
| **Application Load Balancer (ALB)** | Terminates SSL. Only accepts traffic from CloudFront IP ranges. Drop invalid HTTP requests. |

### 1.2 Authentication & Authorization (JWT)

- **Stateless Auth:** API Gateway validates JWTs (RS256 signature) for all protected routes without database lookups.
- **Short-Lived Tokens:** Access tokens expire quickly (e.g., 15 minutes). Refresh tokens are used for session continuation.
- **Role-Based Access Control (RBAC):** Admin endpoints (`/api/v1/products` POST/PUT/DELETE, `/api/v1/sales`) require admin claims in the JWT.
- **Service-to-Service Auth:** Internal requests use internal service tokens or VPC-level network boundaries to prevent unauthorized external access.

### 1.3 Flash Sale Specific Security

- **Admission Tokens:** StormShield issues short-lived (60s), single-use JWTs. The Inventory & Reservation service requires a valid admission token during active flash sales to prevent direct API abuse bypassing the queue.
- **Idempotency Keys:** Required for all state-changing operations (reservations, payments) to prevent duplicate processing.
- **Rate Limiting:** Multi-tiered (WAF IP level, API Gateway user level, StormShield admission rate).

### 1.4 Data Protection

- **Data at Rest:** MongoDB databases, Redis clusters, and RabbitMQ storage volumes are encrypted using AWS KMS managed keys.
- **Data in Transit:** All external and internal service-to-service communication occurs over HTTPS/TLS.
- **Secrets Management:** Passwords, API keys (Payment Gateway, SMS provider), and database credentials are stored in AWS Secrets Manager and injected into containers securely (never hardcoded or in plain env files).
- **PCI Compliance:** GlowRush does **NOT** store credit card numbers. All sensitive payment data is handled via the external Payment Gateway (e.g., Razorpay/Stripe) tokenization flow.

## 2. Observability Architecture

To manage a highly concurrent flash sale, deep visibility is required. We use a unified observability stack based on the "Three Pillars": Metrics, Logs, and Traces.

### 2.1 Metrics (Prometheus + Grafana)

**Key Metrics Tracked:**
- **Request Rate (RPS):** API Gateway total requests, WAF blocked requests.
- **Latency (p50, p95, p99):** API Gateway response times, Inventory `UPDATE` query latency.
- **Error Rates:** HTTP 4xx, 5xx counts per service.
- **Business Metrics:** `inventory_available_quantity`, `stormshield_queue_length`, `successful_payments`, `reservation_failures_out_of_stock`.

**Alerting Thresholds:**
- Critical: API Gateway p95 latency > 1000ms
- Critical: Inventory Service error rate > 5%
- Warning: StormShield queue length > 10,000

### 2.2 Structured Logging (Loki)

- **Format:** All microservices output logs in JSON format to standard out.
- **Content:** Logs include timestamp, log level, service name, message, and `correlationId`.
- **Aggregation:** Loki aggregates logs from all containers for centralized querying via Grafana.
- **Audit Logging:** Admin actions (creating sales, modifying inventory) are explicitly logged with user IDs for auditability.

### 2.3 Distributed Tracing (Jaeger / OpenTelemetry)

- **Correlation ID (`X-Correlation-ID`):**
  - Generated by API Gateway for every incoming request.
  - Passed via HTTP headers in synchronous calls.
  - Included in RabbitMQ message metadata for asynchronous events.
- **Trace Spans:** Services emit spans for database queries, external API calls (Payment Gateway), and message publishing. This allows visualizing the end-to-end path from checkout initiation to order creation.

### 2.4 Monitoring Dashboards

We define two primary Grafana dashboards:
1. **Flash Sale War Room:** Real-time view of API Gateway RPS, StormShield queue size, Inventory remaining stock, Payment success rate, and active database connections. Refresh rate: 1s.
2. **System Health:** CPU/Memory usage per service, RabbitMQ queue depths, database replication lag, and error rates. Refresh rate: 10s.
